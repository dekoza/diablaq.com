HTMX lazy loading on a static site

Diablaq.com · kwiecień 2026

The question: can HTMX be used to load static "partials" so not all images load with the main page?

Short answer: yes, HTMX works perfectly with pre-generated static HTML partials — no server needed. But all cover images already carry loading="lazy", which handles image loading. The real question is whether you want HTMX for UX reasons (accordion sections) rather than raw performance — and where it genuinely helps versus where it adds complexity for nothing.

01 Premise check — what loading="lazy" already handles

Before adding a dependency, understand what you already have

Every cover image in every partial in this codebase already has loading="lazy":

What loading="lazy" does and does not do

What it handles
  • Defers image download until the image is ~one viewport away from the scroll position
  • Requires no JavaScript — it's a native browser feature (supported in all modern browsers since 2019)
  • All 16 covers on /komiksy/ are already lazy — scrolling below the fold is the trigger, not page load
  • Works for any future number of covers too — a 100-project catalog still loads only the visible ones
What it does NOT do
  • The <img> tags themselves are all in the DOM from initial page load — browser must parse, lay out, and hold memory for all of them
  • Does not reduce initial HTML payload — the 13 KB of markup is downloaded regardless
  • Does not give the user a collapsed/expanded UX — all sections are visible and scrollable
  • At 100 projects, the HTML grows to ~80 KB and the DOM has 100+ image nodes even before any images download
Conclusion: At the current catalog size (18 projects, 13 KB HTML), the image loading concern is already solved. Adding HTMX lazy loading for performance reasons alone would be premature optimization. The question becomes: do you want it for UX reasons — specifically the accordion/progressive-reveal interaction pattern?

02 How HTMX works with a static file server

No server-side rendering required — static partials are the "server"

HTMX issues a regular HTTP GET request for whatever URL is in hx-get. It doesn't care whether a dynamic server or a static file sits at that URL. GitHub Pages, Cloudflare Pages — they all serve files over HTTP. That's all HTMX needs.

How it works — request flow User visits /komiksy/ Browser downloads: index.html (13 KB) + diablaq.css + htmx.min.js └── no cover images loaded yet (collapsed sections) User clicks "Główna linia ▼" HTMX fires GET /komiksy/partials/glowna-linia/ GitHub Pages serves: dist/komiksy/partials/glowna-linia/index.html HTMX injects the response HTML into the target <div> Browser renders 10 project cards + starts lazy-loading visible covers What the builder must generate (new files): dist/komiksy/index.html ← main page (headers only, no card content) dist/komiksy/partials/ diablaq/index.html ← bare <div class="tiles">...10 cards...</div> dobre-licho/index.html ← bare <div class="tiles">...4 cards...</div> mecenat/index.html ← bare <div class="tiles">...1 card...</div> studio/index.html ← bare <div class="tiles">...1 card...</div> Partials are bare HTML fragments — no <html>, <head>, or <body>: <div class="tiles"> <article class="project-card">...</article> <article class="project-card">...</article> ...10 more... </div>

Key properties of this approach

  • Static site stays static. The builder generates all files at build time. No runtime computation.
  • CDN-friendly. Partials are cached by the CDN/browser just like any other static file.
  • Partial URLs are real URLs. /komiksy/partials/diablaq/ is a valid page you could link to or bookmark — though it would look odd without context (bare fragment).
  • Same-origin only. Since partials and main page are on the same domain, there are no CORS issues.
HTMX dependency cost: htmx.min.js is ~47 KB raw / ~14 KB gzipped. For a site that currently has zero JavaScript dependencies, this is the first one. It's small by modern standards but not zero. Weigh it against what you get.

03 Pattern A — scroll-triggered load

hx-trigger="revealed" transparent to user

Sections load automatically as the user scrolls toward them. Uses HTMX's revealed trigger, which fires when the element enters the viewport (equivalent to IntersectionObserver). The user sees no explicit interaction — content just appears as they scroll.

Catalog page HTML — initial state
/komiksy/ — skeleton on first load ── Główna linia ────────────────── <div id="s-diablaq" hx-get="/komiksy/partials/diablaq/" hx-trigger="revealed" hx-swap="innerHTML"> [loading placeholder] </div> ── Dobre Licho ─────────────────── <div id="s-dobre-licho" hx-get="/komiksy/partials/dobre-licho/" hx-trigger="revealed" hx-swap="innerHTML"> [loading placeholder] </div>
After scrolling into "Główna linia" viewport
HTMX fires GET /komiksy/partials/diablaq/ Response injected into #s-diablaq: ── Główna linia ────────────────── <div class="tiles"> [Belzebubs ][Ciemny... ] [Człowiek... ][Karmiciel ] [Kodiak ][Mama... ] ...10 cards, images lazy-loaded </div> ── Dobre Licho ─────────────────── [placeholder still — not in viewport yet]
Advantages
  • Completely transparent — user never needs to click anything; content appears naturally as they scroll
  • Well-suited to a browse-and-discover pattern (catalog exploration)
  • Each section request is small (2–4 KB of HTML), fast, cacheable
  • Below-fold sections never load if user doesn't scroll to them
Problems
  • Layout shift. When content loads in, the page height increases suddenly — sections below jump down. Must reserve height with CSS (e.g., min-height on placeholders) to prevent jarring layout shifts (Core Web Vitals: CLS).
  • Scroll position feels unstable on slow connections — user scrolls into a section and content pops in while they're already reading the next one.
  • SEO hole — initial HTML has no project names, covers, or descriptions. See slide 05.

04 Pattern B — accordion expand

click-triggered explicit user intent

Sections are collapsed by default with a visible header. Clicking the header loads and reveals the content. Uses native <details> as the container — HTMX fires on the toggle event, or the <summary> click triggers the request.

/komiksy/ — accordion catalog ┌───────────────────────────────────────────────────────────┐ │ Komiksy │ │ │ │ ▶ Główna linia 12 tytułów [kliknij, by rozwinąć]│ │ ─────────────────────────────────────────────────────── │ │ ▶ Dobre Licho 4 tytuły │ │ ─────────────────────────────────────────────────────── │ │ ▶ Mecenat 1 tytuł │ │ ─────────────────────────────────────────────────────── │ │ ▶ Studio 1 tytuł │ └───────────────────────────────────────────────────────────┘ After clicking "▶ Główna linia": ┌───────────────────────────────────────────────────────────┐ │ ▼ Główna linia 12 tytułów │ │ ┌──┐ ┌──┐ ┌──┐ ┌──┐ ← HTMX loaded, images lazy-load │ │ ┌──┐ ┌──┐ ┌──┐ ┌──┐ │ │ ┌──┐ ┌──┐ │ │ ─────────────────────────────────────────────────────── │ │ ▶ Dobre Licho 4 tytuły │ └───────────────────────────────────────────────────────────┘ Implementation using <details> + HTMX: <details class="catalog-group"> <summary class="catalog-group__head" hx-get="/komiksy/partials/diablaq/" hx-target="#tiles-diablaq" hx-trigger="click once"> ← only load once, ever Główna linia <span class="count">12 tytułów</span> </summary> <div id="tiles-diablaq"></div> </details>
Advantages
  • No layout shift — <details> expands in place, nothing below jumps unexpectedly
  • User expresses intent; content loads because they asked for it
  • hx-trigger="click once" ensures the request fires only the first time — subsequent open/close toggles use the cached DOM
  • Works with the filter pills from the previous deck — "Dobre Licho" pill can open and trigger HTMX load of that section
  • Native <details> degrades gracefully — without JS, the section is open by default (browser's default <details> behavior)
Problems
  • User must click to see any projects — extra friction for first-time visitors who don't know what to expect
  • Still has the SEO problem: project names aren't in initial HTML. See slide 05.
  • Count display ("12 tytułów") in header must be rendered at build time — requires passing edition/project counts to catalog template, not the content itself
  • Combining <details> open state + HTMX loading state requires careful CSS: show spinner while loading, hide once loaded

05 The SEO trap and the only safe pattern

Both Pattern A and B have a hard problem that must be addressed

If project titles, descriptions, and cover URLs are only in HTMX-loaded partials — not in the initial HTML — crawlers that don't execute JavaScript will never see them. This includes most crawlers other than Googlebot, and even Googlebot doesn't guarantee it will wait for async content.

What actually gets indexed without the fix

What a crawler sees when it fetches /komiksy/ (Pattern A or B without fix) <section id="diablaq"> <div hx-get="/komiksy/partials/diablaq/" ...></div> </section> Indexable text on /komiksy/: "Główna linia" "Dobre Licho" "Mecenat" "Studio" That's it. No: Belzebubs, Kodiak, Karmiciel, Mama zabiła mi psa... All project names invisible to SEO.

The progressive enhancement pattern — the only correct approach

Render the full content in the initial HTML exactly as today. On top of that, add HTMX attributes that replace the content with a freshly loaded partial when triggered. The initial HTML is the fallback; HTMX is the enhancement.

Progressive enhancement pattern Initial HTML contains full content (SEO safe, no-JS safe): <details class="catalog-group" open> <summary>Główna linia</summary> <div id="tiles-diablaq" hx-get="/komiksy/partials/diablaq/" hx-trigger="intersect once" hx-swap="outerHTML"> <!-- FULL INITIAL CONTENT: all 10 project cards --> <div class="tiles"><article>Belzebubs...</article>...</div> </div> </details> When JS+HTMX available: the div's content is replaced by the partial (same data, just loaded fresh — allows future personalization hooks) When no JS: full content visible immediately, no HTMX, no UX change When crawler: full content in initial HTML, indexed normally Problem with this pattern: The initial HTML is still full-size. HTMX replaces content that was already there. You gain the UX of deferred rendering but NOT a smaller initial payload. The "save bytes on page load" goal is not achieved. To get a smaller initial payload, you must NOT render full content initially. That requires accepting the SEO tradeoff.

The fundamental tension

You cannot simultaneously have: (1) full content indexed by search crawlers, (2) no content in initial HTML, and (3) zero JS dependency. Pick two.

06 Builder changes — generating static partials

What needs to be added to the generator if you do adopt HTMX

New template: _partials/catalog_section_fragment.html

A bare HTML fragment with no shell — just the grid. No <html>, no <head>, no navigation. Used only for HTMX responses.

{# _partials/catalog_section_fragment.html #}
{# No extends — bare fragment for HTMX consumption #}
<div class="tiles">
  {% for p in projects %}
    {% include "_partials/project_card.html" with context %}
  {% endfor %}
</div>

Builder addition in rendering.py

def render_catalog_partials(
    env, out_dir, site_url, nav_projects, groups, _render_fn, _write_html_fn,
) -> None:
    """Generate bare HTML fragments for each catalog line (HTMX targets)."""
    for group in groups:
        fragment = env.get_template("_partials/catalog_section_fragment.html").render(
            projects=group["projects"],
            abs_url=abs_url(site_url),
        )
        _write_html_fn(
            out_dir / "komiksy" / "partials" / group["id"] / "index.html",
            fragment,
        )
Note: Partial files don't use render_template() — they're bare fragments that deliberately omit nav_projects, site shell, OG tags, etc. They're not pages; they're content chunks. A user who navigates directly to /komiksy/partials/diablaq/ will see an unstyled fragment. That's acceptable but worth documenting.

Changes to catalog.html (accordion variant)

{% for group in groups %}
<details class="catalog-group" {% if loop.first %}open{% endif %}>

New static asset

Copy htmx.min.js to js/htmx.min.js and add a _copy_tree(root / "js", out_dir / "js") call in builder.py::_finalize(). Self-hosting avoids a CDN dependency on a site that currently has none.

07 Where HTMX actually helps: series pages, not catalog

The catalog problem is already solved by loading="lazy". The series page problem is not.

Here's the irony: the catalog page's images are already handled. But the project page for BZIK has a structurally different problem — it renders a flat grid of 12 editions (8 main + 4 eXXXtra) with no way to distinguish them visually until the subseries grouping from the previous deck is implemented. If HTMX is added anywhere, BZIK's project page is the better candidate.

Catalog page — marginal HTMX benefit
  • 16 covers, all loading="lazy" — no images load unless user scrolls there
  • 13 KB HTML — not large enough to benefit from partial loading
  • 4 sections, all visible — reasonable to show all upfront
  • Line groupings are navigation, not content depth — hiding them is artificial friction
  • SEO cost of HTMX pattern > any performance gain at this size
Series page (BZIK) — real HTMX benefit
  • BZIK has 8 + 4 editions today, growing to 20+ over time
  • Two structurally different sub-series (main + eXXXtra) benefit from an accordion
  • User visits /komiksy/bzik/ to browse a specific series — they can tolerate clicking to load sub-series
  • The initial page still shows the project description + cover — useful content is above the fold
  • Editions loaded lazily per subseries = meaningful deferred loading for serial with 20+ covers
/komiksy/bzik/ — HTMX accordion on project page ┌───────────────────────────────────────────────────────────┐ │ Komiksy › BZIK │ │ │ │ [cover] BZIK – Bielski Zin Komiksowy │ │ Nieregularnik mający na celu... │ │ │ │ ▼ BZIK 8 numerów (loaded immediately) │ │ ┌──┐┌──┐┌──┐┌──┐ │ │ ┌──┐┌──┐┌──┐┌──┐ │ │ │ │ ▶ BZIK eXXXtra 4 numery (click to load) │ │ │ └───────────────────────────────────────────────────────────┘ Partials needed: /komiksy/bzik/partials/main/ ← 8 edition tiles (main BZIK) /komiksy/bzik/partials/exxxtra/ ← 4 edition tiles (BZIK eXXXtra) First section open by default — user sees content immediately. eXXXtra section collapsed — user loads it explicitly. This is meaningful: eXXXtra is a separate product track.

Builder support for per-project partials

For this to work, render_project_pages() must also generate subseries partials per project. The logic is the same as catalog partials but at a lower level — group editions by e.subseries, emit one fragment per group.

This makes subseries grouping (Option E from the previous deck) and HTMX accordion a natural combination: the same grouping logic that produces section headers in the non-HTMX case produces partial URLs in the HTMX case.

08 Verdict and recommendation

The honest answer

Yes, HTMX works beautifully with a static site — pre-generated partials are a legitimate pattern and it's a genuinely clever use of the tool. The architecture is clean. The builder change is small. It scales.
But for the catalog page right now, you don't need it. loading="lazy" already defers all images. The catalog HTML is 13 KB. Adding HTMX to solve an image loading problem that doesn't exist yet is premature. The real benefit is UX (accordion interaction), not performance.
Both HTMX patterns (scroll-triggered and accordion) create an SEO problem if the initial HTML doesn't contain the full content. The progressive enhancement workaround preserves SEO but doesn't reduce the initial payload — it only adds the accordion UX on top. Be clear about which goal you're actually solving before implementing.

Recommendations by use case

→
Goal: reduce image loading on catalog page.
Already solved by loading="lazy". Do nothing. Revisit if images are not lazy-loaded for some reason in future.
→
Goal: add accordion UX to catalog (lines collapse/expand).
Use the progressive enhancement pattern: full content in initial HTML + <details> + HTMX replaces content on expand. Adds HTMX dependency. Accordion UX is gained; initial payload is not reduced. Worth it if the publisher wants that interaction pattern. Implement with filter pills (Option A, previous deck) so pill + accordion work together.
→
Goal: genuinely defer image loading for large series (BZIK, future series).
Use HTMX accordion on the project page, per subseries. First subseries preloaded (open), others lazy-loaded. This is the strongest case for HTMX here — real deferred loading where the content is deep and the structure is meaningful.
→
Goal: reduce initial payload on catalog when it grows to 100+ projects.
At that scale: implement Pattern B (accordion) without progressive enhancement, accept that sub-line catalog pages won't be indexed from the main /komiksy/ URL — but those projects all have their own pages at /komiksy/{slug}/ which are always fully rendered. The individual project pages are what gets indexed anyway.
