Overview

What we're looking at

Diablaq is a Polish indie comic-book publisher. The site is a custom static generator (Python + Jinja2) using Pico CSS as the base framework, overlaid with a hand-written diablaq.css. The visual identity leans on a dark-red brand colour and uppercase headings. On paper, a solid foundation. In practice, multiple layers of neglect have piled up that undermine every page the user visits.

Stack
Python SSG · Jinja2 · Pico CSS
CSS framework
pico.min.css + diablaq.css (1052 lines)
Heading font
Roboto Condensed … not loaded 💀
Templates
10 pages + 6 partials
Brand colour
3 different reds. One brand.
Social meta
Zero OG tags. Zero Twitter cards.

#1

The hero is just two lines of textCritical

The homepage hero is the single most important screen real-estate on the entire site. For a comic book publisher — an inherently visual medium — the hero contains exactly one heading and one tagline, with zero imagery, zero CTA, zero visual energy. There is also no .home-hero CSS rule anywhere in the stylesheet, so the wrapper is a semantically empty shell with no visual treatment at all. A first-time visitor has no idea what kind of books Diablaq makes, who they are for, or what to do next.

✗ Before — templates/home.html
<section class="home-hero">
  <header class="page-header">
    <h1>Wydawnictwo Diablaq</h1>
    <p class="page-header__lead">
      Piekielnie dobre komiksy!
    </p>
  </header>
</section>

<!-- .home-hero has ZERO CSS rules. -->
<!-- No background. No image. No CTA. -->
<!-- No scroll indicator. Nothing. -->
✓ After — with visual hero
<section class="home-hero">
  <div class="home-hero__bg">
    <!-- collage of 3 cover images -->
    <img src="{{ featured[0].cover }}"
         aria-hidden="true">
  </div>
  <div class="home-hero__copy">
    <h1>Piekielnie dobre komiksy</h1>
    <p>Polski niezależny komiks.</p>
    <a href="/publikacje/"
       class="hero-cta">
      Zobacz katalog
    </a>
  </div>
</section>
Fix — Add a full-bleed hero with a collage of 3–4 cover images, a dark overlay gradient, the tagline in large type, and a primary CTA button ("Zobacz katalog"). The publisher already has beautiful cover art — use it. Even a single cover as a blurred background transform this from "blank page" to "brand statement".

#2

Newsletter button goes nowhere — and tells users whyCritical

The newsletter section sits on every single page of the site, in the global footer area. Its CTA button has href="#". Clicking it scrolls to the top and does nothing. Worse: the implementation note left in the Jinja comment is an HTML comment that ships to the browser — users who open DevTools read "Link podmienimy na docelowy formularz (np. MailerLite) gdy będzie gotowy" ("We'll replace the link with the target form when ready"). This is developer scaffolding treated as a production feature. It destroys trust.

✗ Before — templates/base.html
<a class="site-newsletter__button"
   href="#"
   role="button">
  Zapisz się
</a>
<p class="site-newsletter__hint">
  <small>Link podmienimy na docelowy formularz
  (np. MailerLite) gdy będzie gotowy.</small>
</p>
✓ After — minimal inline form
<form class="newsletter-form"
      action="https://app.mailerlite.com/…"
      method="post"
      target="_blank">
  <label for="nl-email" class="sr-only">
    E-mail</label>
  <input id="nl-email" type="email"
         name="email"
         placeholder="twój@email.pl"
         required>
  <button type="submit">Zapisz się</button>
</form>
Evidence — base.html:95: href="#" on the CTA button. base.html:96–97: the hint paragraph visible to all users. Appears on every page render since it lives in the global layout.
Fix — Either wire up a real MailerLite/Brevo embed form, or remove the section entirely until it's ready. A dead CTA button is worse than no CTA at all — it trains users that buttons on this site don't work.

#3

Dates are raw ISO strings — programmer output, not UXMajor

Every date visible to users — edition release dates, blog post dates — is rendered via .isoformat(), producing machine-readable strings like 2024-11-15. This is what you output to a JSON API, not a Polish-language website for comic book readers. The pattern appears in at least three templates. It signals "nobody proofread this."

✗ Before — 3 templates, same mistake
<!-- edition_tile.html -->
<p class="edition-tile__meta">
  <small>
    {{ e.release_date.isoformat() }}
  </small>
</p>

<!-- blog_post.html -->
<time datetime="{{ post.date.isoformat() }}">
  {{ post.date.isoformat() }}
</time>

<!-- edition_details.html -->
<small>{{ edition.release_date.isoformat() }}</small>
✓ After — human-readable, still semantic
{# In a Jinja2 global filter (rendering.py): #}
def format_date_pl(d):
    MONTHS = ["stycznia", "lutego",
              "marca", "kwietnia", ...]
    return f"{d.day} {MONTHS[d.month-1]} {d.year}"

<!-- templates -->
<time datetime="{{ post.date.isoformat() }}">
  {{ post.date | format_date_pl }}
</time>

<!-- renders as: 15 listopada 2024 -->
Fix — Register a format_date_pl Jinja2 filter in rendering.py and replace all .isoformat() display calls. Keep .isoformat() only in datetime attributes for machine readability. One filter, three fixes.

#4

The heading font is declared but never loadedCritical

Every heading, nav item, and card title specifies font-family: var(--diablaq-font-heading), which resolves to "Roboto Condensed". But fonts.css contains a comment admitting the font isn't actually fetched: "mapujemy Roboto Condensed -> systemowy stack, aby uniknąć hostowania fontów z niewiadomą licencją". No @font-face, no Google Fonts @import. On most devices "Roboto Condensed" is not installed, so the browser falls through to system-ui. The entire typographic identity the design was built around simply doesn't render.

✗ Before — css/fonts.css
/* Fonty dopasowane do makiet Penpot.
   Uwaga: mapujemy Roboto Condensed ->
   systemowy stack, aby uniknąć
   hostowania fontów z niewiadomą
   licencją. */

:root {
  --diablaq-font-heading:
    "Roboto Condensed",
    system-ui, "Segoe UI", Roboto, …;
}

/* No @import. No @font-face.
   Roboto Condensed ≠ Roboto.
   Falls through to system-ui on
   99% of devices. */
✓ After — actually load it
/* Roboto Condensed is Apache 2.0 —
   free to use via Google Fonts. */
@import url(
  'https://fonts.googleapis.com/css2?
  family=Roboto+Condensed:wght@400;
  600;700&display=swap'
);

/* OR self-host via fontsource: */
/* npm i @fontsource/roboto-condensed */

:root {
  --diablaq-font-heading:
    "Roboto Condensed", system-ui;
}
Evidence — fonts.css:4–7: comment explicitly states the font is not hosted. diablaq.css uses var(--diablaq-font-heading) in ~12 rules. Roboto Condensed is published under Apache 2.0 — there is no licence problem. The comment is wrong.
Fix — Add a single @import from Google Fonts or self-host via @fontsource/roboto-condensed. The Apache 2.0 licence permits free commercial use. This is a one-line fix that unlocks the entire typographic system the designer intended.

#5

Placeholders are invisible on a dark backgroundMajor

Blog card placeholders use background: rgba(0,0,0,0.06). The site body background is --color-bg: #000 — pure black. A 6% opacity black on black is completely invisible: contrast ratio ≈ 1.06:1. The person-card initials placeholder puts muted text in the same near-invisible box. When a cover image is missing, users see a blank void, not a graceful fallback.

✗ Before — diablaq.css
.blog-card__cover-placeholder {
  background: rgba(0, 0, 0, 0.06);
  /* on #000 body → invisible void */
}

.person-card__photo {
  background: rgba(0, 0, 0, 0.06);
}

.person-card__placeholder {
  color: var(--pico-muted-color);
  /* muted on near-black = unreadable */
}

/* --color-bg: #000 (root) */
/* rgba(0,0,0,0.06) on #000  */
/* = contrast ratio 1.06:1   */
/* WCAG minimum: 3:1 for UI  */
✓ After — visible on dark bg
.blog-card__cover-placeholder {
  background: #1c1c1c;
  /* subtle lift, clearly visible */
  display: grid;
  place-items: center;
}

.blog-card__cover-placeholder::after {
  content: "";
  width: 40px; height: 40px;
  background: url("/img/icon.png")
              center/contain no-repeat;
  opacity: 0.25;
}

.person-card__photo {
  background: #1c1c1c;
}

.person-card__placeholder {
  color: #52525b; /* zinc-600 */
}
Fix — Replace all rgba(0,0,0,0.06) placeholder backgrounds with a flat dark value like #1c1c1c. Optionally add a faint centred logo icon as the placeholder visual. Also audit every use of Pico's --pico-muted-color: on a pure-black background it likely fails contrast requirements.

#6

Card covers have no hover feedback — they feel brokenMajor

Every edition tile, project card, and blog card cover is a clickable <a>. None of them have a hover state. The cursor doesn't change to a pointer either — cursor: pointer is set on three nav elements but not on any card cover link. Users hovering over comic covers get zero visual confirmation the element is interactive. The only card type with hover CSS is .project-card__cover--text — the text-only fallback version, not the image one. Priorities are inverted.

✗ Before — no hover on cards
.edition-tile__cover {
  display: block;
  position: relative;
  /* no cursor, no hover → feels static */
}

.project-card__cover {
  display: block;
  position: relative;
  /* same — zero interactive feedback */
}

.blog-card__cover {
  display: block;
  /* same */
}

/* cursor: pointer only appears on
   .nav-links__group summary (l.183)
   .nav-mobile__links summary (l.416)
   .person-hero__more-btn  (l.1046)
   Not on any content card. */
✓ After — clear interactive affordance
/* Single rule catches all card covers */
.edition-tile__cover,
.project-card__cover,
.edition-card__media,
.blog-card__cover {
  cursor: pointer;
  transition: opacity 0.18s ease,
              transform 0.18s ease;
}

.edition-tile__cover:hover,
.project-card__cover:hover,
.edition-card__media:hover,
.blog-card__cover:hover {
  opacity: 0.88;
  transform: translateY(-2px);
}

/* Respect reduced-motion */
@media (prefers-reduced-motion: reduce) {
  .edition-tile__cover,
  .project-card__cover { transition: none; }
}
Fix — Add the hover ruleset above. The translateY(-2px) lift is subtle enough not to shift layout but gives clear physical feedback. Add @media (prefers-reduced-motion) to respect accessibility settings. One block of CSS, covers every content card on the site.

#7

The brand uses three different reds simultaneouslyMajor

The CSS root block defines three distinct red values that are all used as the primary brand colour: the CSS keyword darkred (#8b0000), the hex #8b0000 again as --diablaq-red-dark, and rgb(172, 53, 31) (#ac351f) as --diablaq-red. Then --pico-primary-hover adds a fourth: #b00000. The topbar header background and the footer links are different reds. Brand identity requires one primary colour, used consistently.

✗ Before — 4 reds in one file
:root {
  /* Pico overrides */
  --pico-primary: darkred;           /* #8b0000 */
  --pico-primary-hover: #b00000;    /* #b00000 */

  /* Brand tokens */
  --diablaq-red: rgb(172, 53, 31);  /* #ac351f */
  --diablaq-red-dark: #8b0000;      /* #8b0000 */

  /* All used as "the brand red":
     topbar bg   → --diablaq-red
     nav links   → --diablaq-red-dark
     link hover  → --diablaq-red
     Pico buttons→ darkred
     Four values. One brand. */
}
✓ After — one source of truth
:root {
  /* Single brand decision */
  --brand:       #ac351f;  /* primary */
  --brand-dark:  #8b1a0a;  /* hover/dark */
  --brand-light: #c8502e;  /* active/focus */

  /* Pico overrides reference brand */
  --pico-primary:            var(--brand);
  --pico-primary-hover-background:
                             var(--brand-dark);

  /* Legacy aliases (remove gradually) */
  --diablaq-red:      var(--brand);
  --diablaq-red-dark: var(--brand-dark);
}
Evidence — diablaq.css:3 darkred · :7 #b00000 · :38 rgb(172,53,31) · :39 #8b0000. Four values across 12 usage sites. A user hovering a nav link sees a different red than the topbar background.
Fix — Decide on one canonical hex (the logo colour is the source of truth — sample it). Replace all four values with two CSS variables: --brand and --brand-dark. Point Pico's override variables at them. Delete the redundant aliases once transitioned.

#8

Navigation never shows where you areMajor

There is no active/current state on any navigation link — desktop or mobile. A user on the /blog/ page sees the same nav as a user on /ludzie/. No underline, no highlight, no weight change. This is a basic wayfinding primitive that every multi-page site needs. The CSS has no .active, [aria-current], or .is-current rule. The templates pass no current-page context to the base layout.

✗ Before — base.html (nav)
<ul class="nav-links">
  <li><a href="/blog/">Blog</a></li>
  <li><a href="/zapowiedzi/">Zapowiedzi</a></li>
  <li><a href="/nowe/">Nowości</a></li>
  <!-- all links look identical -->
  <!-- no aria-current, no .active -->
  <!-- no current_url in context   -->
</ul>
✓ After — aria-current + CSS
{# builder.py / rendering.py:
   pass current_path to every template #}

<li><a href="/blog/"
   {% if current_path.startswith('/blog/') %}
   aria-current="page"
   {% endif %}>Blog</a></li>

/* CSS — no extra class needed */
.nav-links a[aria-current="page"] {
  text-decoration: underline;
  text-underline-offset: 0.3em;
  text-decoration-thickness: 2px;
  opacity: 1;
}
Fix — Pass current_path (the output URL) from the SSG render context into base.html. Use aria-current="page" on the matching link — this is the semantically correct attribute and also gives you the CSS hook for free. Works for both desktop nav and mobile nav without duplicating logic.

#9

Social sharing produces a blank unfurl on every pageMajor

The <head> in base.html has exactly one meta tag: charset. No og:title, no og:image, no og:description, no Twitter Card. When someone shares a comic edition link on Facebook, Twitter/X, or WhatsApp, they get the raw URL with no preview. For a publisher whose catalogue covers are the product, this is a catastrophic missed opportunity — every share that could have shown a gorgeous cover image instead shows nothing.

✗ Before — base.html <head>
<head>
  <meta charset="utf-8">
  <meta name="viewport" …>
  <title>…</title>
  <!-- canonical link (good) -->
  <link rel="stylesheet" …>
  <link rel="icon" …>
  <!-- NO og:title          -->
  <!-- NO og:description    -->
  <!-- NO og:image          -->
  <!-- NO twitter:card      -->
  <!-- NO description meta  -->
</head>
✓ After — full social head
{# Pass og_image, og_desc from context #}
<meta name="description"
      content="{{ og_desc or site_desc }}">

<meta property="og:type"      content="website">
<meta property="og:title"     content="{{ page_title }}">
<meta property="og:description" content="{{ og_desc }}">
<meta property="og:image"
      content="{{ og_image or '/img/logo.png' }}">
<meta property="og:url"       content="{{ canonical_url }}">

<meta name="twitter:card"  content="summary_large_image">
<meta name="twitter:image" content="{{ og_image }}">
Fix — Add the meta block to base.html with Jinja2 variables. Each template (edition, blog post, project) passes its cover image as og_image and summary as og_desc. The SSG already has all this data — it just doesn't surface it in the head. OG image recommended size: 1200×630px.

#10

Missing covers fall back to the 32px favicon, stretchedMajor

Both edition_tile.html and project_card.html use /img/icon.png as the fallback when no cover image is set. icon.png is the site favicon — a small square icon designed for 16–32px display. The card covers are rendered at an aspect-ratio: 180/255 with object-fit: cover. The result is a tiny icon stretched and pixelated across a full card cell. It doesn't say "cover coming soon" — it says "this site is broken."

✗ Before — edition_tile.html & project_card.html
{# edition_tile.html #}
<img
  src="{{ e.cover_image or '/img/icon.png' }}"
  alt="{{ e.title }}"
  loading="lazy">

{# project_card.html #}
{% else %}
  <img src="/img/icon.png"
       alt="{{ p.title }}"
       loading="lazy">
{% endif %}

<!-- icon.png: favicon, ~32px square
     Card slot: 180×255px portrait
     Result: blurry stretched mess -->
✓ After — CSS placeholder, no bad image
{# edition_tile.html — conditional render #}
{% if e.cover_image %}
  <img src="{{ e.cover_image }}"
       alt="{{ e.cover_alt or e.title }}"
       loading="lazy">
{% else %}
  <div class="cover-placeholder"
       aria-label="{{ e.title }}">
    <span class="cover-placeholder__text">
      {{ e.title[:2] | upper }}
    </span>
  </div>
{% endif %}

/* CSS */
.cover-placeholder {
  aspect-ratio: 180 / 255;
  background: linear-gradient(135deg,#1c1010,#2d1515);
  display: grid; place-items: center;
  border-radius: var(--pico-border-radius);
}
Fix — Remove or '/img/icon.png' from both templates. Replace with an explicit {% if %}/{% else %} block that renders a CSS-only placeholder with the first two letters of the title. Dark gradient background, muted text — visually intentional, not accidentally broken.

#12

29 !important declarations signal a CSS architecture collapseMinor

diablaq.css contains 29 !important declarations across 1052 lines — roughly one every 36 lines. The majority fight Pico CSS's default spacing on .container, <details>, and nav elements. This is the hallmark of CSS written reactively: something looked wrong, so !important was added to force it. Each !important makes the next bug harder to fix and signals that the cascade is not understood or controlled. This isn't catastrophic today, but it compounds.

✗ Before — recurring pattern
.site-header .container {
  padding-top: 0 !important;
  padding-bottom: 0 !important;
}

.nav-links {
  margin: 0 !important;
}

.nav-links > li {
  margin: 0 !important;
}

.nav-links__group details {
  display: inline-flex !important;
  margin: 0 !important;
  padding: 0 !important;
  background: transparent !important;
  border: 0 !important;
  color: #fff !important;
}
/* … 20 more like this */
✓ After — override at the root
/* Pico v2 supports CSS variable overrides.
   Suppress Pico defaults at :root level
   instead of fighting them inline. */

:root {
  /* Kill Pico's nav/details padding
     before it reaches components */
  --pico-nav-element-spacing-vertical: 0;
  --pico-nav-element-spacing-horizontal: 0;
  --pico-form-element-spacing-vertical: 0;
}

.site-header .container {
  padding-block: 0;
  /* no !important needed */
}

/* For details/summary: use
   appearance: none + custom styles
   rather than overriding Pico's
   opinionated component defaults */
Fix — Read Pico v2's CSS variable reference and override defaults at :root rather than at every usage site. For the <details>/<summary> nav elements, Pico's opinionated styles are too aggressive — consider using plain elements with custom CSS instead of fighting the framework. Reduce !important count to zero as a quality metric.

The codebase is structurally sound — it just needs someone to treat it like a finished product, not a prototype left in production.
