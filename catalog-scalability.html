/komiksy/ — Scalability Proposals

Diablaq.com · kwiecień 2026

Problem: The new /komiksy/ catalog page groups all 18 projects under 4 section headers on one scroll. Today that's manageable. The main line already has 12 projects in a 4-column grid (3 rows). Adding 10 more makes it a wall. BZIK already has 12 editions (8 main + 4 eXXXtra) with no end in sight. Two separate clutter problems → two separate solution families.

01 Problem anatomy — two distinct clutter axes

Understanding the problem before reaching for a solution

Axis 1 · Catalog page — too many projects
/komiksy/ — today (18 projects) ── Główna linia ───────────────── [ ][ ][ ][ ] row 1 [ ][ ][ ][ ] row 2 [ ][ ][ ][ ] row 3 ← ok today ── Dobre Licho ────────────────── [ ][ ][ ][ ] 1 row ← ok today ── Mecenat ────────────────────── [ ] 1 project ← ok today ── Studio ─────────────────────── [ ] 1 project ← ok today /komiksy/ — tomorrow (40 projects) ── Główna linia ───────────────── 8 rows of 4 covers ← wall of covers no way to find anything no filtering, no search
Axis 2 · Project page — too many editions
/komiksy/bzik/ — today (12 editions) ── Wydania ─────────────────────── [01][02][03][04] row 1 (main) [05][06][07][08] row 2 (main) [x1][x2][x3][x4] row 3 (eXXXtra) ← 3 rows, 2 unmarked groups, ok-ish /komiksy/bzik/ — year 3 (24 editions) ── Wydania ─────────────────────── 6 rows of 4 covers main + eXXXtra interleaved no visible grouping no indication which are read no sense of structure Also affects: Spółka ZŁO (2 → likely 12+) Kodiak (2 → ongoing) MidGuard (1 → series) Człowiek-Cieć (2 → ongoing)

Why these need separate answers

Catalog clutter is a discovery problem — users can't find the series they want in a wall of covers. Series clutter is a comprehension problem — users can't understand the structure of a series when all issues are undifferentiated.

Solutions that help catalog clutter (filter by line, sub-pages) don't help series clutter. Solutions that help series clutter (subseries grouping, pagination) don't help catalog clutter. Evaluate each axis independently.

What we're not solving here

Mobile scroll length, image loading performance, and per-edition search are real concerns but out of scope. This deck covers information architecture only.

02 Catalog A — client-side filter pills

0 new pages ~30 lines of vanilla JS no builder changes

Add a row of pill buttons above the grid. Clicking a pill hides all projects not matching that line. No page reloads, no new URLs.

/komiksy/ ┌────────────────────────────────────────────────────────────────┐ │ Komiksy │ │ Wszystkie serie i tytuły wydawnictwa Diablaq. │ │ │ │ [● Wszystkie] [ Główna linia ] [ Dobre Licho ] [ Mecenat ] [ Studio ] │ │ │ │ ── Główna linia ─────────────────────────────────────────── │ │ [ ][ ][ ][ ] │ │ [ ][ ][ ][ ] ← shows/hides entire section on pill click │ │ │ │ ── Dobre Licho ───────────────────────────────────────────── │ │ [ ][ ][ ][ ] │ │ │ │ ... etc │ └────────────────────────────────────────────────────────────────┘ When "Główna linia" pill active: ┌────────────────────────────────────────────────────────────────┐ │ [ Wszystkie ] [● Główna linia] [ Dobre Licho ] ... │ │ │ │ ── Główna linia ─────────────────────────────────────────── │ │ [ ][ ][ ][ ] │ │ [ ][ ][ ][ ] │ │ [ ][ ][ ][ ] ← still potentially many rows │ │ ← Dobre Licho section hidden │ └────────────────────────────────────────────────────────────────┘
Advantages
  • Zero new pages → no URL fragmentation
  • No builder changes at all
  • Graceful degradation: without JS, page shows all sections (same as today)
  • State could persist via URL hash: /komiksy/#glowna-linia
  • Trivial to add — ~30 lines of vanilla JS
  • Works for a catalog of any size
  • Pill state is visible: user always knows what's filtered
Limitations
  • Does not reduce the number of items visible — just hides other lines. Main line still shows 12+ projects in a flat grid.
  • Each line still an undifferentiated flat grid. Doesn't help discovery within a line.
  • Requires JS — though graceful degradation mitigates this.
  • Lines don't have "landing page" identity: filtering to Dobre Licho gives no context about what Dobre Licho is.
  • Doesn't scale past ~60 projects on a single page (scroll fatigue).

Implementation

Each project card gets a data-line="diablaq" attribute. Each section gets a matching data-line. The JS filter shows/hides by matching attribute. Active state stored in data-active on the filter bar. No Jinja changes — just a new <script> block in catalog.html.

// ~25 lines, zero dependencies
document.querySelectorAll('.catalog-filter-btn').forEach(btn => {
  btn.addEventListener('click', () => {
    const line = btn.dataset.line;
    document.querySelectorAll('.catalog-section').forEach(section => {
      section.hidden = line !== 'all' && section.dataset.line !== line;
    });
    document.querySelectorAll('.catalog-filter-btn').forEach(b =>
      b.setAttribute('aria-pressed', b === btn ? 'true' : 'false')
    );
    if (line !== 'all') location.hash = line;
  });
});

03 Catalog B — sub-line pages under /komiksy/

+4 new pages builder change no JS

Each publication line gets its own full-grid page at a sub-URL. The top-level /komiksy/ becomes a lightweight overview linking to each line.

URL structure /komiksy/ ← lightweight overview (see below) /komiksy/glowna-linia/ ← full grid, line=diablaq projects /komiksy/dobre-licho/ ← full grid, line=dobre-licho /komiksy/mecenat/ ← full grid, line=mecenat /komiksy/studio/ ← full grid, line=studio /komiksy/ — overview layout ┌────────────────────────────────────────────────────────────────┐ │ Komiksy │ │ │ │ Główna linia → Przeglądaj│ │ Autorskie komiksy dla dorosłych. │ │ [ ][ ][ ][ ] ← 4 newest/featured only + "See all 12 →" │ │ │ │ Dobre Licho → Przeglądaj│ │ Imprint komiksowy dla dzieci i młodzieży. │ │ [ ][ ][ ][ ] │ │ │ │ Mecenat → Przeglądaj│ │ Publikacje rozwijane w formule mecenatu. │ │ [ ] │ │ │ │ Studio → Przeglądaj│ │ Produkcje komiksowe dla innych wydawców. │ │ [ ] │ └────────────────────────────────────────────────────────────────┘ /komiksy/glowna-linia/ — full grid ┌────────────────────────────────────────────────────────────────┐ │ Komiksy › Główna linia │ │ Autorskie komiksy dla dorosłych. │ │ [ ][ ][ ][ ] ← all 12 (or 30) projects │ │ [ ][ ][ ][ ] │ │ ... │ └────────────────────────────────────────────────────────────────┘
Advantages
  • Each line gets identity: its own URL, heading, description — Dobre Licho can explain what it is for children's audience; Mecenat can explain the crowdfunding model.
  • Header nav links go to line sub-pages directly, replacing the old "Publikacje" dropdown cleanly.
  • /komiksy/ becomes compact — always short, regardless of catalog size.
  • No JS required. Pure static.
  • Scales to any number of projects — each line page still manageable.
  • Natural landing page for line-specific social/ad campaigns.
Limitations
  • 4 new pages to generate and maintain.
  • Builder change: render_catalog_page() must emit both an overview and sub-line pages.
  • Still a flat grid within each line — with 30 main-line projects, the sub-page has the same problem at a smaller scale.
  • Mecenat and Studio sub-pages each have 1 project — almost pointless as pages in their own right.
  • Overview page requires a curated description per line (content work).

Implementation

Add a line description field to the builder config (a dict in rendering.py). render_catalog_page() generates /komiksy/index.html (overview with 4 tiles per line) and /komiksy/{line-slug}/index.html (full grid). One new template: catalog_line.html.

04 Catalog C — genre/tag static pages

+N new pages model change content tagging work

Add a tags field to project frontmatter. The builder generates /komiksy/tag/{tag}/ pages (same mechanism as blog tags). Tags cut across lines, enabling discovery by genre rather than publisher imprint.

Example tags applied to current catalog Spółka ZŁO → tags: [superbohaterski, komedia, zeszytowy] Kodiak → tags: [horror, komedia, superbohaterski] Karmiciel → tags: [horror, noir, superbohaterski] BZIK → tags: [antologia, mecenat, underground] Pisto → tags: [przygoda, dzieci, dobre-licho] Mama zabiła → tags: [obyczajowy, autobiograficzny] Generated pages: /komiksy/tag/horror/ ← Kodiak, Karmiciel /komiksy/tag/superbohaterski/ ← Spółka ZŁO, Kodiak, Karmiciel /komiksy/tag/dzieci/ ← Pisto, Rodzina Ciekawskich, mksp /komiksy/tag/antologia/ ← BZIK /komiksy/ — with tag cloud ┌────────────────────────────────────────────────────────────────┐ │ Komiksy │ │ │ │ Przeglądaj według gatunku: │ │ [horror] [superbohaterski] [dzieci] [przygoda] [noir] │ │ [antologia] [obyczajowy] [sci-fi] ... │ │ │ │ ── Główna linia ─────────────────────────────────────────── │ │ [ ][ ][ ][ ] │ │ ... │ └────────────────────────────────────────────────────────────────┘
Advantages
  • Richest discovery model — cuts across lines (horror fans get Kodiak + Karmiciel regardless of imprint).
  • SEO value: /komiksy/tag/horror/ is a crawlable page with semantic meaning.
  • Reuses the existing blog tag machinery (same builder pattern).
  • Can serve as metadata for future features (filtering, related projects).
  • Enables linking from blog posts: "more horror comics →"
Limitations
  • Requires someone to tag all 18 (and future) projects — non-trivial content work.
  • Tag taxonomy must be decided upfront and maintained (typos, synonyms, drift).
  • Doesn't reduce the catalog grid itself — tags are a supplement, not a replacement for grid organization.
  • Tag pages with 1–2 projects look thin until catalog grows.
  • Most useful at 30+ projects — overkill now.

Implementation

Add tags: list[str] to Project model in models.py. Parse from frontmatter in parsing.py (same as blog post tags). Add render_project_tag_pages() in rendering.py. Template: reuse or fork listing.html with project cards instead of edition tiles. Estimated: 3–4 hours of code + N hours of tagging content.

05 Catalog D — magazine overview + full grids

+4 new pages template redesign no JS

This is the Dark Horse model: /komiksy/ is a curated magazine-style overview showing each line's featured or newest items with a strong visual header. Full grids live on sub-pages, but /komiksy/ is the destination for browsers — not a filing cabinet.

/komiksy/ — magazine layout ┌────────────────────────────────────────────────────────────────┐ │ │ │ GŁÓWNA │ │ LINIA Przeglądaj → │ │ ┌─────────────────────────┐ ← big featured cover │ │ │ │ + 3 newest │ │ │ [featured cover] │ ┌──┐ ┌──┐ ┌──┐ │ │ │ │ │ │ │ │ │ │ │ │ └─────────────────────────┘ └──┘ └──┘ └──┘ │ │ │ │ DOBRE LICHO Przeglądaj → │ │ Komiksy dla dzieci i młodzieży. │ │ ┌──┐ ┌──┐ ┌──┐ ┌──┐ │ │ │ │ │ │ │ │ │ │ │ │ └──┘ └──┘ └──┘ └──┘ │ │ │ │ MECENAT Przeglądaj → │ │ ┌──┐ │ │ └──┘ │ └────────────────────────────────────────────────────────────────┘
Advantages
  • Best-looking option — feels like a publisher's catalog, not a database export.
  • /komiksy/ is always compact regardless of catalog size: N lines × (1 featured + 3 tiles).
  • Lines have distinct visual identity through header typography.
  • Featured project drives editorial attention ("what should people buy this month").
  • No JS needed. Static sub-pages.
  • Scales to 100 projects: overview stays short, sub-pages are the full grids.
Limitations
  • Most complex to implement — requires "featured project per line" logic, modified layout.
  • Requires the same 4 new sub-pages as Option B.
  • Mecenat and Studio still have 1 project each — their overview rows look anemic.
  • Featured project selection needs editorial attention (either manual featured: true in YAML or auto-select newest).
  • The home.html already shows a similar featured + grid layout — may create redundancy between homepage and catalog page.

How it differs from Option B

Option B (sub-line pages) makes /komiksy/ a navigation hub — a list of links. Option D makes /komiksy/ a destination — a browsable magazine front with actual covers. Both generate the same sub-line full-grid pages. The difference is in what /komiksy/index.html renders.

Key insight

Option A alone does not solve the problem — it only hides non-active lines. If "Główna linia" has 40 projects, filtering to it still shows 40 in an unbroken grid. Option A is a complement to sub-line pages (B or D), not an alternative.

Option D (magazine) is strictly better than B for the visitor experience. It costs the same number of pages and slightly more template work. The only reason to choose B over D is if the team won't maintain featured-per-line editorial picks.

Series clutter — a separate problem

07 Series E — subseries grouping

0 new pages model already supports it template change only

The Edition model already has a subseries field. BZIK already uses it: 8 main issues have subseries: null, 4 eXXXtra issues have subseries: "eXXXtra". The template simply doesn't use it. Fix the template, get structure for free.

Current /komiksy/bzik/ — undifferentiated
── Wydania ────────────────────── [01][02][03][04] [05][06][07][08] [x1][x2][x3][x4] ← main issues and eXXXtra interleaved by release date no visual distinction user doesn't know what eXXXtra is
Proposed /komiksy/bzik/ — grouped
── BZIK ───────────────────────── [01][02][03][04] [05][06][07][08] ── BZIK eXXXtra ───────────────── [x1][x2][x3][x4] ← clear visual grouping user instantly sees 2 tracks each subseries can grow independently

Template change

In project.html, instead of a flat {% for e in editions %}, group editions by e.subseries. Render a section header per group. Jinja's groupby filter handles this in ~5 lines. Editions with subseries: null are the "main series" group.

{# project.html — grouped edition rendering #}
{% set null_label = project.title %}
{% for group_key, group_editions in editions | groupby('subseries') %}
  <h3>{{ group_key or null_label }}</h3>
  <div class="tiles">
    {% for e in group_editions %}
      {% include "_partials/edition_tile.html" with context %}
    {% endfor %}
  </div>
{% endfor %}
Advantages
  • Zero new pages.
  • Model already supports it — data is there, template just ignores it.
  • Works for any series that uses subseries in frontmatter.
  • Scales naturally: each subseries section grows independently.
  • Helps both BZIK and any future anthology/subseries.
Limitations
  • Doesn't help when a single subseries grows beyond ~20 items.
  • Requires tagging all existing BZIK editions with the correct subseries field (BZIK already has it; others need it if they split).
  • Section headers need styling — minor CSS addition.

08 Series F — static pagination on project pages

+pages per series builder change no JS

When a project has more than PAGE_SIZE editions (proposed: 12), the builder generates additional pages: /komiksy/bzik/ (first 12), /komiksy/bzik/strona/2/ (next 12), etc. Prev/next navigation links at the bottom.

/komiksy/bzik/ — page 1 of 2 ┌────────────────────────────────────────────────────────────────┐ │ Komiksy › BZIK │ │ │ │ [cover] BZIK – Bielski Zin Komiksowy │ │ Nieregularnik mający na celu... │ │ │ │ ── Wydania ──────────────────────────────────────── │ │ [01][02][03][04] │ │ [05][06][07][08] │ │ [09][10][11][12] │ │ │ │ ← Poprzednia Strona 1 z 2 Następna → │ └────────────────────────────────────────────────────────────────┘ /komiksy/bzik/strona/2/ ┌────────────────────────────────────────────────────────────────┐ │ Komiksy › BZIK strona 2 │ │ [13][14][15][16] ← page 2 │ │ ... │ │ ← Poprzednia Strona 2 z 2 Następna → │ └────────────────────────────────────────────────────────────────┘
Advantages
  • Prevents any project page from growing unbounded.
  • Clean URLs — no JS, crawlable.
  • Works alongside subseries grouping (pagination applies per subseries).
Limitations
  • Pagination is a last resort UX pattern — it means the user must decide to load more. Subseries grouping + "show all" toggle is friendlier.
  • Significant builder complexity: chunking editions, generating multiple pages per project, injecting prev/next links.
  • Only BZIK needs this now. Building it for one project with 12 issues is premature.
  • Canonical URL handling gets complicated — which page is "the" project page for SEO?

Verdict

Static pagination is the right tool for a project with 30+ editions. For a project with 12–20 editions grouped by subseries, subseries section headers (Option E) are sufficient and much simpler. Implement F only if/when a project's subseries itself exceeds 20 items.

09 Growth model — when each solution is needed

Not all solutions are needed now. This maps catalog size to the right intervention — implement each step when the trigger is reached, not before.

  • Option A: filter pills on /komiksy/

  • Add line_description to builder config
  • Option C: genre tags (if content team willing)

  • Client-side search (lunr.js) when full catalog exceeds ~60 projects

Why this sequencing

Filter pills (A) costs near-nothing and immediately improves the page for first-time visitors who know they want "Dobre Licho" books. It degrades gracefully. Do it now.

Subseries grouping (E) is a template fix with data that already exists. BZIK's 12 issues are visually chaotic today. Do it now.

Magazine overview (D) requires editorial commitment to pick featured projects and write line descriptions. Don't implement until the catalog is large enough that the current page actually feels cluttered — currently it's three short sections.

Genre tags (C) require tagging all content. High editorial cost for the current catalog size. Implement when you have enough projects that genre is a meaningful filter (30+).

Pagination (F) is a last resort. BZIK will need it eventually but not for years. Avoid until forced.

10 Recommendation + implementation notes

Recommended plan
Now Option E: subseries grouping in project.html — 5 lines of Jinja, zero builder changes, fixes BZIK today.
Now Option A: filter pills in catalog.html — ~30 lines of JS, zero builder changes, helps navigation immediately.
When catalog reaches ~30 projects Option D: magazine overview + sub-line pages — converts /komiksy/ into a proper publisher front page with line identities.
When catalog reaches ~50 projects Option C: genre tags — add tags to Project model and emit tag pages using the blog tag machinery.
When a series exceeds ~20 editions Option F: static pagination — add pagination support to render_project_pages().

Phase 1 implementation: Option E (subseries grouping)

File: templates/project.html. Replace the flat edition loop with a grouped render. Jinja's groupby filter groups an iterable by attribute; None values sort to a configurable position.

{% set grouped = editions | groupby('subseries') %}
{% for subseries, group_editions in grouped %}
  {% if grouped | length > 1 %}
    {# Only render header if there actually are multiple groups #}
    <header class="section-header">
      <h3>{{ subseries or project.title }}</h3>
    </header>
  {% endif %}
  <div class="tiles">
    {% for e in group_editions %}
      {% include "_partials/edition_tile.html" with context %}
    {% endfor %}
  </div>
{% endfor %}

Caveat: Jinja's groupby sorts groups by key, placing None (no subseries) first alphabetically as an empty string. Verify sort order matches desired display order (main series first, eXXXtra second). If not, pre-sort in Python before passing to template.

Phase 1 implementation: Option A (filter pills)

File: templates/catalog.html. Add a filter bar above the first section, emit data-line attributes on each .catalog-section, add inline JS (or a small catalog.js file).

The filter bar must be rendered from the same groups list the template already has — no new builder data needed. The "Wszystkie" pill resets to showing all sections.

What not to do

  • Don't add pagination now. BZIK has 12 issues. That's 3 rows in a 4-column grid. This is not a UX emergency.
  • Don't build sub-line pages now. "Mecenat" is 1 project. A sub-page for 1 project is not a sub-page, it's a redirect with extra steps.
  • Don't add genre tags now. Tagging 18 projects consistently requires a stable taxonomy. Settle the vocabulary when you have enough projects to reveal patterns.
  • Don't use infinite scroll. It's incompatible with static site generation without JS, breaks browser history, and is hostile to accessibility.
